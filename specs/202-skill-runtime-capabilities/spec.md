# 壳专用技能与能力清单规范源（202-skill-runtime-capabilities）—— 规格

> **Module / Status: Proposed / Last Updated: 2026-10-11 / 上游基线: opencode v2.0.26（Branch_v2.0.26）**
>
> **证据口径**：✅ 实测 ｜🔶 沿用 ｜⬜ 待验证。
> **定位**：本模块是**壳专用技能**（随包投放、讲「这台设备能做什么/不能做什么」的那份文档）与**能力清单**之间的**规范源**：规范源是权威，技能是它的运行期摘要，**单向派生**。

## 1. 模块概述

### 1.1 目的

把「设备能力边界」从「技能正文」提升为**规范源**，并给技能的维护建立可核验的规则：

1. 规范源 = `docs/鸿蒙环境能力清单.md`（能力 × 状态 × 根因层 × 证据来源）+ `docs/toybox命令清单.md`（命令可达性）+ 各 `specs/0NN-*`（能力契约）+ `docs/ACL申请清单.md`（权限边界）。
2. 运行期摘要 = `skills/<name>/SKILL.md`（随包投放，由模型按需读取）：只写结论与用法，不写证据链。
3. **派生方向单向**：先改规范源，再同步技能；技能被发现与规范源不一致时，以规范源为准并立即修正技能。

### 1.2 解决的问题

| # | 问题 | 影响 |
|---|---|---|
| 1 | 能力边界散落在能力清单、规格、技能三处，读者要自己拼 | 结论漂移；评审无法定位权威版本 |
| 2 | **过期的能力摘要比没有摘要更有害**：技能若仍写「本设备没有 shell」，模型会**拒绝使用**已交付的 shell 能力（同型工程已有先例 🔶，其修正被单独记录） | 已交付能力被闲置，用户看到的是「模型不干活」 |
| 3 | 能力变化没有同步机制（能力加了、技能没改） | 漂移只会在使用现场暴露 |
| 4 | 技能可能承诺**未获批权限**带来的能力（如桌面目录直写） | 与 ACL 现实冲突，使用者按提示操作却失败 |

### 1.3 范围

**包含**：

- 壳专用技能的内容**最小要求**（必须覆盖的能力域与必须标注的降级）。
- 能力清单 ↔ 技能的**派生规则与同步触发条件**。
- 漂移检查（构建期 / 评审期）：技能里出现的命令名与能力声明必须能在规范源中找到对应条目。
- 版本与日期绑定（技能记录它对应的能力清单版本）。

**不包含**：

- 技能正文的具体措辞创作（属文档写作，不属规格）。
- 技能框架本身的实现（发现路径、加载时机、工具面）——上游契约，见 §7 待验证项。
- 插件机制（`specs/201-plugin-runtime/`）、命令执行契约（`specs/010-tool-shell/`）、搜索兜底与 PTY 专项（Phase 2）。

## 2. 用户故事

- 作为**使用者**，我希望模型知道在这台设备上该怎么干活（能用哪些命令、越界了怎么办、什么功能注定不可用），而不是反复试错。
- 作为**使用者**，我希望新交付的能力（如 shell）立刻被模型使用，而不是被一份过期说明挡住。
- 作为**维护者**，我希望只有一处权威结论；能力变了只改一处，另一处由规则保证同步。
- 作为**评审者**，我希望技能里不得出现「未获批权限带来的能力承诺」。

## 3. 功能需求

> 编号：`FR-202-NNN`。

| 编号 | 需求 | 强度 | 来源 / 状态 |
|---|---|---|---|
| FR-202-001 | 壳专用技能内容 MUST 由规范源派生；维护顺序 MUST 为「先改规范源，再改技能」；MUST NOT 出现「技能有、规范源无」的结论 | MUST | 设计决策（同型工程的治理规则 🔶） |
| FR-202-002 | 技能 MUST 至少覆盖：① 可用命令集与禁用项（无 `bash` / `git` / `rg` / `curl`；命令必须是 toybox 可达集合内）② 无 PTY / 无交互式程序 ③ 路径围栏与审批语义（越界会被拒、如何申请更宽范围）④ 数据与项目目录语义（项目根可写、数据在沙箱内）⑤ 插件档位现状（默认不启用安装） | MUST | `docs/鸿蒙环境能力清单.md` §2、`specs/010-tool-shell/`、`specs/011-workspace-auth/`、`specs/201-plugin-runtime/` |
| FR-202-003 | 技能 MUST NOT 声称设备不具备的能力；能力交付后 MUST 同步删除对应的「不可用」表述（过期表述视为缺陷） | MUST | 🔶 同型工程先例：技能未同步导致模型拒绝使用已交付工具 |
| FR-202-004 | 技能 MUST NOT 承诺未获批权限带来的能力（例：桌面目录直写、后台常驻保活），并 MUST 说明「授权 + 重启」这类前置条件 | MUST | `docs/ACL申请清单.md` §4/§5；`docs/鸿蒙环境能力清单.md` #8/#13 |
| FR-202-005 | 技能 MUST 标注能力缺口与**降级方式**（如内容搜索「返回空 + 明示」，不得静默失败） | MUST | `docs/工程规划-V2.md` §7.3、§7.4 |
| FR-202-006 | 技能 MUST 说明**观测纪律**：结论以应用域为准；`hdc shell` 视角可能骗人（`/data/service/hnp` 被 SELinux 隐藏、`readlink /proc/self/exe` 误报） | SHOULD | `docs/鸿蒙环境能力清单.md` §1.3 |
| FR-202-007 | 构建期 MUST 提供漂移检查：技能中出现的命令名 MUST 属于规范源声明的三类之一（直接可达 / 仅 `toybox <n>` / 不存在并已标注），否则失败 | MUST | 设计决策（`docs/toybox命令清单.md` §1 为判定集合） |
| FR-202-008 | 技能文件 MUST 记录其对应的规范源版本与日期；能力清单版本变化 MUST 触发技能复核（记录在案） | MUST | 设计决策 |
| FR-202-009 | 技能的**发现路径与文件契约** MUST 与上游 v2 契约一致，MUST NOT 自造目录名或文件名 | MUST | `docs/工程规划-V2.md` §4.1（`skills/`）、§4.3（映射为 opencode `SKILL.md` 技能）；⬜ 具体契约本工程核对 |
| FR-202-010 | 技能内容 SHOULD 保持「一页可读」：只写结论与操作要点，证据链留在规范源 | SHOULD | 设计决策 |
| FR-202-011 | 技能与规范源的一致性 MUST 纳入验收：技能中的每条能力结论都能在规范源定位到出处（章节或条目编号） | MUST | 设计决策 |

## 4. 关键实体

| 实体 | 说明 | 关键属性 |
|---|---|---|
| `SkillDocument` | 壳专用技能正文 | `name`、`path`、`specVersion`（对应能力清单版本）、`sections[]` |
| `CapabilitySnapshot` | 供技能引用的能力快照 | `capabilities[]`（能力 / 状态 / 根因层 / 处置）、`commands`（三分类）、`permissions`（已获批 / 不申请） |
| `DriftCheck` | 漂移检查结果 | `unknownCommands[]`、`staleClaims[]`（技能声称不可用但已交付）、`missingClauses[]`（缺少必备能力域） |
| `SyncTrigger` | 触发技能复核的事件 | `capabilityAdded` / `capabilityRemoved` / `permissionChanged` / `tierChanged` |

## 5. 验收场景

### 场景 1：能力交付后同步

- **Given** shell 能力（`specs/010-tool-shell/`）交付，规范源中该项状态由 ❌/⬜ 变为 ✅（本工程实测后）
- **When** 执行技能同步
- **Then** 技能中不再出现「本设备没有 shell」类表述；技能 `specVersion` 更新；漂移检查通过

### 场景 2：漂移被拦住

- **Given** 技能写了一个规范源中不存在、且不属于「不存在集合」的命令名
- **When** 执行构建期漂移检查
- **Then** 检查失败并列出该命令名（阻断流水线）

### 场景 3：能力域缺失

- **Given** 技能未覆盖「路径围栏与审批」或「插件档位」
- **When** 执行必备域检查
- **Then** 报告缺失项（`missingClauses`）并失败

### 场景 4：不得承诺未获批权限

- **Given** `READ_WRITE_DESKTOP_DIRECTORY` 为 `system_basic` + `user_grant`（2026-10-14 起由 `006-signing-identity` 声明并随 ACL 批次申请；未获批或用户未授权时**不可直写**）
- **When** 审查技能正文
- **Then** 技能中不存在「可直接写入桌面目录」类承诺；用户目录相关表述必须带授权与重启前置

### 场景 5：降级必须明示

- **Given** 内容搜索在 v1 不可用
- **When** 模型按技能指引尝试搜索
- **Then** 结果为**空 + 明示**（而非静默失败），技能已写明该降级

## 6. 非功能需求

- **单一权威**：能力的权威结论只在规范源；技能只做摘要（避免二次维护）。
- **可机检**：命令名、必备章节、版本绑定三类检查 MUST 可脚本化。
- **可追溯**：技能每条结论可定位到规范源出处（章节 / 条目编号）。
- **交付安全**：技能不得包含未获批权限的能力承诺、不得包含未验证设备的实测口吻（⬜ 项必须保持 ⬜ 标注）。
- **体积**：技能正文 SHOULD 控制在一页量级，避免模型上下文浪费。

## 7. 假设与约束

**假设（逐条待验证）**

- ⬜ **待验证** 1：opencode v2 的技能文件契约与**发现路径**（目录名、文件形态、是否需要前置元数据、是否随包投放即可生效）—— MUST 与上游源码核对后固定，本规格不预设具体路径。
- ⬜ **待验证** 2：技能是否需要在宿主内注册（类似「技能目录注入」的机制），以及随包投放（只读区）是否满足其加载方式。
- ⬜ **待验证** 3：技能被加载的时机（进程启动即注入 vs 会话首次请求前）与模型可见形态（名称 + 截断描述 + 按需加载正文）。
- ⬜ **待验证** 4：是否存在与技能等价的「能力提示」UI 通道（用于非模型可见的降级提示），以及是否需要与之保持一致。
- 🔶 **沿用** 5：同型工程的经验 —— 技能未随能力交付同步，会直接导致模型拒绝使用已交付工具；该先例是本模块存在的直接动因。

**约束**

- 约束 1：技能**不得**成为权威来源；任何与规范源冲突的表述以规范源为准。
- 约束 2：技能**不得**承诺未获批权限带来的能力（`docs/ACL申请清单.md`）。
- 约束 3：本模块**不新增**任何设备能力，只做规范化与同步治理。
- 约束 4：未实测的能力在技能中 MUST 保持「待验证 / 不可用」表述，不得提前写成可用。
