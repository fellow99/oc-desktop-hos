## 1. 项目概述

### 1.1 一句话定义

把 opencode 的桌面形态移植到鸿蒙 PC / OpenHarmony 桌面：用 `harmonypc-electron` 提供的 Electron-on-HarmonyOS 运行时承载 Electron 主进程，在**独立 utility 进程**内**进程内托管** opencode 的服务端（Node bundle），渲染层直接加载该服务端**同源托管的内嵌 Web UI**，最终打包为可签名分发的 HAP。

### 1.2 关键结论速览

| 维度 | 结论 | 决策出处 |
|---|---|---|
| 目标形态 | 鸿蒙 PC 桌面应用，`deviceTypes: ["2in1", "tablet"]` | §1.1、§4.1 |
| 应用名 / 包名 | OC Desktop / `rg.fellow99.oc.OCDesktop` | §3.7 |
| 工程组织 | `opencode-workspace` **submodule 并行容器**，还原 `../兄弟目录` | §3.1 |
| 骨架来源 | **复制 `dsh-desktop-hos` 的工程框架与 electron 相关内容**后改造 | §3.0 |
| 运行时 | Electron **37**（`v37.2.3-20260825.1`），Electron 40 备选，不使用 34 | §3.3 |
| 服务端宿主 | **utility 进程** `utilityProcess.fork(sidecar.js)` | §3.2 |
| 渲染层 | 服务端**内嵌 UI 同源托管** → `loadURL("http://<局域网IP>:<port>/")` | §3.5 |
| 上游产物 | 打补丁新增 `script/build-node-harmony.ts`，构建**含真实内嵌 UI** 的 Node bundle | §3.4 |
| 数据持久化 | **better-sqlite3**（真机 `node:sqlite` 无 binding） | §3.6 |
| v1 目标 | **MVP 先行**：核心链路端到端可用，原生重依赖打桩降级 | §7、§10 |
| 分发 | tar.gz + SHA-256 marker，运行时流式解压到沙箱 | §6.3 |

## 2. 参考工程调研结论

### 2.1 opencode 上游：如何"以服务方式启动"

证据：`../opencode/packages/web/src/content/docs/server.mdx`、`../opencode/packages/opencode/src/cli/cmd/{serve,web}.ts`（✅ 源码核实）。

- `opencode serve` 启动**无头 HTTP 服务**，把实例暴露为 **OpenAPI 3.1**（`GET /doc`）。默认 `--port 4096`、`--hostname 127.0.0.1`；`--cors <origin>` 可多次追加；`--mdns` 启用服务发现。
- 鉴权：设 `OPENCODE_SERVER_PASSWORD` 后对 `serve` 与 `web` 同时启用 **HTTP Basic**，用户名默认 `opencode`（可用 `OPENCODE_SERVER_USERNAME` 覆盖）。未设密码时进程会打印 "server is unsecured" 警告。
- `opencode web` = 起同一服务 + 打开系统浏览器。
- 数据面：REST（`/session`、`/session/:id/message`、`/file`、`/find`、`/config`、`/agent`、`/provider`…）+ **SSE**（`GET /event`，首事件 `server.connected`；`GET /global/event`）；另有 `/tui/*` 供 IDE 插件驱动。
- `Server.listen({ port, hostname, cors?, username?, password? })` 为对外入口（`packages/opencode/src/server/server.ts`）。

**决定性发现 —— 服务端默认同源托管内嵌 Web UI**（✅ 源码核实）：

`packages/opencode/src/server/ui/index.ts` 的行为分两支：

1. **未设** `OPENCODE_DISABLE_EMBEDDED_WEB_UI`（默认）：从构建期生成的 `opencode-web-ui.gen.ts`（路径 → 资源文件映射）在**根路径**返回 SPA（`/` → `index.html`），HTML 附 CSP（`default-src 'self'; connect-src 'self'`）。
2. **已设**该开关：改为反向代理 `https://app.opencode.ai`。

对上层的意义：**只要内置真实 UI 资源，一个 `http://<host>:<port>/` 就同时提供 UI 与 API**（同源），无需独立前端工程、无需自定义协议、无需 preload 桥、无 CORS 问题。

**桌面端既有实现**（`packages/desktop-electron`，Electron 40.4.1 + electron-vite，✅ 源码核实）：

- `src/main/server.ts#spawnLocalServer` 名为 sidecar，**实为进程内**：`await import("virtual:opencode-server")` → `Server.listen({ port, hostname: "127.0.0.1", username: "opencode", password })`；`prepareServerEnv` 设 `OPENCODE_CLIENT=desktop`、`XDG_STATE_HOME=userData` 等。
- `src/main/index.ts` 全局设 `OPENCODE_DISABLE_EMBEDDED_WEB_UI=true`，因此它自己在**渲染进程**打包 `@opencode-ai/app`。
- `electron.vite.config.ts` 把 `virtual:opencode-server` 解析到 `../opencode/dist/node/node.js`。

**Node 服务端构建**（`packages/opencode/script/build-node.ts`，✅ 源码核实）：

- `Bun.build({ target: "node", entrypoints: ["./src/node.ts"], outdir: "./dist/node", external: ["jsonc-parser", "@lydell/node-pty"], files: { "opencode-web-ui.gen.ts": "" } })`。
- **该 `files` 注入的是空字符串** → 标准 `dist/node` **不含**真实 UI，根路径会 404。这正是必须自建"harmony 版构建脚本"的原因（§3.4）。
- 另一个构建 `script/build.ts` 产出 **Bun 编译的单文件二进制**（`bun-linux-arm64` 等目标），**无 ohos 目标** → 鸿蒙不可用。

**运行时适配层**（条件导入，✅ 源码核实）：

| 导入别名 | bun 分支 | node 分支（本工程走这条） |
|---|---|---|
| `#db` | `src/storage/db.bun.ts` | `src/storage/db.node.ts` → **`node:sqlite` 的 `DatabaseSync`** |
| `#pty` | `src/pty/pty.bun.ts` | `src/pty/pty.node.ts` → `@lydell/node-pty`（原生模块） |
| `#hono` | `src/server/adapter.bun.ts` | `src/server/adapter.node.ts` → `@hono/node-server` + `@hono/node-ws` |

CORS 语义：`src/server/middleware.ts#CorsMiddleware` 仅在来源命中白名单（`http://localhost:*`、`http://127.0.0.1:*`、`tauri://*`、`*.opencode.ai`、`--cors` 追加项）时**回写 CORS 响应头**，**不拒绝**任何请求（✅ 源码核实）。因此同源加载不需要改 CORS。

其他：渲染层是 `packages/app`（SolidJS SPA，✅）；`packages/web` 是 Astro/Starlight **文档站**，不是 UI（避免误判）。本工程消费的上游版本由 submodule 固定为 `v1.4.3-142-g7a6ce05d09`。

它是本工程**之前的同型尝试**，已真机跑通框架级链路，产物可直接借鉴（但**不作为本工程骨架基线**，见 §3.0）：

- 真机实测硬约束（🔶 沿用，全部来自真机验证）：

| 约束 | 结论 |
|---|---|
| 主进程 spawn | `child_process.spawn('sh', …)` 挂起至 watchdog 超时；`spawnSync` 卡死整进程 |
| utility 进程 spawn | **正常**：`utilityProcess.fork` → `startChildProcess` → `runArkProcess`；`spawnSync('sh',['-c','echo hi'])` exit 0 |
| `node:sqlite` | **FAIL（No such binding: sqlite）** —— 华为定制 Node 无该 binding |
| `process.platform` | 真机为 **`'openharmony'`**（不是 `'ohos'`） |
| 回环网络 | 渲染进程访问 `127.0.0.1` 被 **loopback 隔离** → 必须绑 `0.0.0.0` + 经局域网 IP 连接 |
| symlink | `EACCES`（须用 copy 物化） |
| 临时目录 | `/tmp` 与 `os.tmpdir()` 沙箱不可写，`TMPDIR` 无效，需 monkey-patch `os.tmpdir` |
| 家目录 | `homedir()` = `/storage/Users/currentUser`，**不可写**（EPERM） |
| 可用命令 | toybox：`sh ls cat cp rm mkdir find grep sed awk` + 第三方应用提供的 `node`/`npm`/`python3`；**无 git / rg / bash / curl** |
| 大文件数目录 | 957 个文件直接入 HAP 会卡死 hvigor 或令 Electron 启动时 CHECK 崩溃 → 必须 tar.gz + 运行时流式解压 |
| bundleName | 改名**已被对照实验排除**为崩溃根因（`ParseAssetsOHOS` 能正确按 bundle 挂载 resfile）→ 自定义包名可行 |

- 旧工程与真机环境：设备 HAD-W24 / API 24 / HarmonyOS 6.1.0.135（另一台 HAD-W32 也验证过）。
- 与旧工程的关系定位：**它的结论全部继承，它的骨架不复用**。骨架按 §3.0 从 `dsh-desktop-hos` 复制。

## 3. 核心决策

### 3.0 骨架来源：复制 `dsh-desktop-hos` 的工程框架 ✅ 已确认

本工程**不从零搭骨架**，也**不复用旧工程 `opencode-harmony` 的目录**：以 `dsh-desktop-hos` 为**唯一的工程框架镜像源**，复制其工程框架与 `electron` 相关内容（`AppScope` / `electron` / `web_engine` / `hvigor` / `build-profile.json5` / `hvigorfile.ts` / `oh-package.json5` / `code-linter.json5` / `signing.*.sample` / `scripts` 骨架 / `specs` 与 `docs` 规范），再把业务接线改为 opencode。逐项"保留 / 剔除 / 替换"对照见 §4.3。

选择理由：

1. 它是**已迭代上线**的同型工程（当前 0.2.0），签名注入、产物投放、overlay 保护、流式解压等机制均已踩平，不必重新发现；
2. 骨架与 Electron-on-HarmonyOS 运行时天然配套 —— 其 `electron/` 模块本身即来自 `harmonypc-electron`；
3. 复用它已成型的 `specs/` 与 `docs/` 规范，本工程文档体系无需重新发明。

**镜像边界：只镜框架，不搬业务。**

| 处置 | 内容 |
|---|---|
| ✅ **继承** | 目录结构、构建流水线形态、幂等补丁机制、overlay 机制、单文件大产物 + 流式解压、`docs/` 四件套、`specs/NNN` 编号规范 |
| 🔁 **替换** | 补丁集（dsh → opencode）、插件与技能、overlay 条目、`src-main/` 业务接线 |
| ❌ **剔除** | `profiles/`（profile/pnpm 装配）、市场运行时、`dsh-dist` 分发形态 —— opencode 侧无对应物 |

旧工程 `opencode-harmony` 的角色：**结论继承、骨架不复用** —— 它的 4 个补丁与真机实测结论作为本工程补丁集（§6.2）与风险表（§11.1）的输入，见 §2.4。

### 3.1 目录组织：`opencode-workspace` submodule 并行容器 ✅ 已确认

`opencode-workspace` 是一个**聚合容器仓库**，用 **git submodule 固定各仓库版本**，把本工程需要的全部并行工程汇聚到一处，使各构建脚本期望的 `../兄弟目录` 布局在容器内即可解析。

```
opencode-workspace/                      # 本仓库 —— submodule 容器（普通目录 + submodule 混合）
├── opencode/                            # [submodule] 上游源码 —— 被消费（源码引用 + 补丁）
├── oc-desktop-hos/                      # [submodule] **本工程**（HAP 鸿蒙工程）
├── harmonypc-electron/                  # [submodule] Electron-on-HarmonyOS 运行时（SO + ArkTS 桥）
├── harmonypc-electron-versions/         # （普通目录）运行时发行版归档 + 头文件指南
└── oc-desktop-website/                  # [submodule] 本工程产品官网（本版不填内容）
```

**消费契约**（每个脚本只依赖这些相对路径）：

| 本工程使用 | 来源 | 方式 |
|---|---|---|
| `../opencode` | submodule | **源码引用**：幂等打补丁 → 构建 Node bundle |
| `../harmonypc-electron` | submodule | **物理拷贝**：`electron/` + `web_engine/` + SO + 运行时资源 |
| `../harmonypc-electron-versions` | 普通目录 | 备选运行时归档 + 原生模块重编译材料 |
| `../oc-desktop-website` | submodule | 官网（Phase 3 才动） |

**为什么是"物理拷贝"而不是 HAR `file:` 依赖**（🔶 沿用结论）：hvigor 只构建 `build-profile.json5` 中**物理存在**的模块；HAR 的 `file:` 依赖只带纯 ArkTS，**不带 `.so` 与 `resfile`**。因此运行时必须以 `collect-runtime` 脚本物理拷贝进来。

**为什么采用 submodule 并行**：与 `deepseek-harness-workspace` 完全同构（上游 + 壳工程 + 运行时 + 归档 + 官网五件套），版本可复现、`../` 解析确定、升级靠指针推进。代价是升级需显式 bump 指针 —— 这是期望行为。

> 说明：这与旧工程早期"同级目录 + 源码引用（**非** submodule）"的结论**有意不同**。此处以**本工作区的既有事实**为准（容器已建成），并把"submodule 并行"确立为本工程规范。

### 3.2 服务端宿主形态：**utility 进程 sidecar** ✅ 已确认

三个候选：

| 方案 | 说明 | 结论 |
|---|---|---|
| **(a) utility 进程 sidecar** | `utilityProcess.fork(src-main/sidecar.js)`，sidecar 内 `import` opencode Node bundle 并 `Server.listen` | ✅ **选定** |
| (b) 主进程进程内 | 上游 `desktop-electron` 的做法（`import("virtual:opencode-server")`） | ❌ 鸿蒙不可用：主进程 spawn 挂起 → `bash`/`shell` 工具不可用 |
| (c) 独立 ELF 服务进程 | 把 opencode 编译成独立二进制再 spawn | ❌ 不可行：无 ohos 目标的 Bun 产物；自备 ELF 需**二进制证书**（AGC `certType: 4`），个人开发者不可得 |

选定 (a) 的理由：① 真机实测**utility 进程内 `spawn` 正常**，`bash` 与 `shell` 工具原生可用，无需 ArkTS 桥代跑命令；② 服务端崩溃不带走 UI 主进程；③ 与旧工程已验证路径一致。

代价（写进风险）：utility 进程的**退出不可观测**、僵尸进程需自管；sidecar 生命周期需与 `before-quit`/`will-quit` 绑定。

### 3.4 上游产物来源：**补丁新增 `build-node-harmony.ts`** ✅ 已确认

### 3.5 渲染层：**内嵌 UI 同源加载**（不需要 web shim）✅ 已确认

```
Renderer(BrowserWindow)  --loadURL-->  http://<局域网IP>:<port>/
                                        ├── GET /            → 内嵌 SPA（index.html + assets）
                                        ├── GET /session...  → REST API
                                        └── GET /event       → SSE 事件流
```

因为 UI 与 API **同源**（同一 `host:port`），达成：

- **零 CORS**、**零鉴权配置歧义**（同源不需要 CORS 头）、**零自定义协议**、**零 preload 桥**、**零 UI 代码改动**；
- 不需要把 `@opencode-ai/app` 打进渲染进程（与上游 desktop 路径相反：上游关掉内嵌 UI 然后自己装 UI；我们**保留内嵌 UI**）；
- 因此也**不需要** `packages/app` 的 web shim。

唯一必须的两个接线点（都在**主进程**，不碰 UI 代码）：

1. **回环隔离规避**：服务端绑 `0.0.0.0`，渲染层用局域网 IP 访问。
2. **请求头改写**：主进程拦截发往该 `host:port` 的请求，把 `Host`/`Origin` 改写为 `127.0.0.1:<port>`（继承 dsh 的 `installLoopbackHeaderRewrite` 思路）；同一钩子可顺带注入 `Authorization`（见 §5.4 安全）。

⬜ 待验证：`Host`/`Origin` 改写对 opencode 是否**必需**（opencode 的 `CorsMiddleware` 不拒绝请求，理论上可省）—— 实测决定；保留该钩子作为兜底。

## 5. 运行架构

### 5.1 进程模型

```
EntryAbility（Electron 主进程，electron/ 模块）
 │  ├─ 环境装配：HOME / XDG_* / PATH / tmpdir 修正（§5.3）
 │  ├─ 建窗：先显示 loading 页（避免白屏）
 │  ├─ 确保产物就位：tar.gz → 流式解压到 userData（marker 幂等，§6.3）
 │  ├─ 起 sidecar：utilityProcess.fork(src-main/sidecar.js)
 │  │     └─ import <opencode-dist>/node.js
 │  │          └─ Server.listen({ hostname: "0.0.0.0", port: <随机空闲端口>, username, password })
 │  │          └─ 内嵌 UI 同源托管（不设 OPENCODE_DISABLE_EMBEDDED_WEB_UI）
 │  ├─ 健康检查：轮询 GET /global/health（带 Basic 凭据）
 │  ├─ 安装请求头钩子：对 http://*:port/* 改写 Host/Origin（+ 注入 Authorization）
 │  ├─ loadURL("http://<局域网IP>:<port>/")
 │  └─ before-quit / will-quit：kill sidecar（含僵尸清理）
 └─ 渲染进程（Electron BrowserWindow × N）
      └─ 同源：加载 SPA、调 REST、订阅 SSE（/event）
```

为什么"先 loading 页再 loadURL"：首次启动要解压产物（数十秒量级），直接 `loadURL` 会长时间白屏（沿用 dsh 与旧工程做法）。

### 5.2 启动时序（失败可见）

```
启动 → [env] 环境装配 → [artifact] 产物就位（含首次解压）
   ├─ 失败 → loading 页显示具体阶段与原因（fail-visible，不静默降级）
   → [sidecar] fork 成功？ → 失败则终止并报错
   → [health] /global/health 就绪（超时上限 30s）
   → [load] loadURL(logical URL) → did-finish-load → 关闭 loading 页
```

规则：**每个阶段都必须可观测**（日志 + loading 页阶段文本）；不允许"卡住但不说"。

### 5.3 沙箱与目录映射

真机沙箱事实（🔶 沿用，§2.4）：`homedir()` 不可写；`/tmp` 与 `os.tmpdir()` 不可写；`/data`、`/storage` 根 `readdir` 受限；symlink `EACCES`。

映射方案：

| 变量 | 目标 | 理由 |
|---|---|---|
| `HOME` / `USERPROFILE` | `/data/storage/el2/base/files`（userData） | 让"家目录"可写 |
| `XDG_DATA_HOME` | `<userData>/data` | 落地 `opencode/opencode.db` 与认证凭据。上游 `desktop-electron` 的 `sqliteFileExists()` 读的正是 `XDG_DATA_HOME/opencode/opencode.db`（无该项时回落到 `homedir()/.local/share/opencode/opencode.db`），**必须保证该路径可写** |
| `XDG_CACHE_HOME` | `<userData>/cache` | 缓存 |
| `XDG_STATE_HOME` | `<userData>`（与上游一致；如需细分可用 `<userData>/state`） | ⬜ 上游 `desktop-electron` 就把该项**直接指向 userData**，本工程沿用同一取值以减少与上游行为差异 |
| `TMPDIR` | 设为 `<userData>/tmp`，**并 monkey-patch `os.tmpdir()`** | 真机上环境变量对 Node 无效，必须打补丁 |
| `PATH` | 前置可用工具目录，其余保持系统默认 | `bash` 工具要能找到 `sh`/`node`/`grep` 等 |
| `OPENCODE_CLIENT` | `desktop` | 与上游 desktop 一致（⬜ 待验证对行为的实际影响） |
| `OPENCODE_SERVER_PASSWORD` / `..._USERNAME` | 随机密码 / `opencode` | 见 §5.4 安全 |

**不设** `OPENCODE_DISABLE_EMBEDDED_WEB_UI`（保留内嵌 UI，这是 §3.5 的前提）。

### 5.4 网络与安全

| 项 | 方案 | 状态 |
|---|---|---|
| 绑定地址 | `0.0.0.0` + 随机高位端口 | 必需（回环隔离） |
| UI 访问 | `http://<局域网IP>:<port>/` | 必需 |
| 请求头改写 | 主进程对发往该端口的请求改 `Host`/`Origin` 为 `127.0.0.1:<port>` | 🔶 兜底；⬜ 验证是否必需 |
| 鉴权 | 设 `OPENCODE_SERVER_PASSWORD`，主进程用同一钩子注入 `Authorization: Basic ...` | ⬜ **推荐引入**：因为绑 `0.0.0.0` 意味着**同局域网任何主机都能访问本服务**（对一个有文件读写与命令执行能力的编码代理而言，风险不可接受）。用主进程钩子注入凭据可保持"零 UI 改造" |
| 代理 | `NO_PROXY` / `no_proxy` 追加 loopback 与局域网地址 | 🔶 沿用 |
| 证书/CA | 系统 CA 行为未验证 | ⬜ 见 §11 O4 |

若实测证明 `Host`/`Origin` 改写不必要，钩子仍需保留用于**注入 Basic 凭据**。

### 5.5 项目目录与授权

opencode 的"项目"语义由**目录**决定（`GET /project/current`、`GET /path`）。hvigor 侧真机事实：应用只能自由读写自己的沙箱，用户目录需**按实际路径**申请授权（`/storage/Users/currentUser/{Documents,Desktop,Download}` 等）。

设计（⬜ 需实测定型，见 §11 O3）：

1. 应用启动后由 ArkTS 侧弹出**目录选择器**，用户选定工作目录；
2. 授权走 `fileShare.activatePermission` / `requestDirectoryPermission`，**必须传实际路径**；
3. 选定目录传递给 sidecar，作为服务端的项目根 / 初始目录；
4. UI 内切换项目时复用同一授权通道。

## 8. 权限与签名

### 8.1 必须申请（ACL，受限权限）

判定规则（🔶 沿用 dsh 的权威口径）：**受限权限 ⟺ `provisionEnable == true` 且 `availableLevel ∈ {system_basic, system_core}`**。仅凭名称含 `kernel.` 就主张申请是错的。

| 权限 | level / since | 状态 | 用途 |
|---|---|---|---|
| `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY` | system_basic / since 14 / 平板+2in1 / 受限 | ⬜ **本包名需新申请**（dsh 已为其包名获批） | 启用 Electron/V8 **JIT**，引擎必需，**不可删除**；须同时出现在 `web_engine` 的 `requestPermissions` 与 `definePermissions` |

### 8.2 开放权限（免 ACL，写进 `requestPermissions` 即安装时授予）

`INTERNET`、`GET_NETWORK_INFO`、`KEEP_BACKGROUND_RUNNING`（配合 `backgroundModes: ["taskKeeping"]`）、`READ_WRITE_DOCUMENTS_DIRECTORY`、`READ_WRITE_DOWNLOAD_DIRECTORY`、`FILE_ACCESS_PERSIST`。

### 8.3 本项目**不需要**申请（相对 dsh 的净简化）

| 项 | 不申请的理由 |
|---|---|
| 二进制证书（AGC `certType: 4`） | 本工程**不随包分发自有 ELF**（服务端跑在 Electron 自带 Node 里），无需"用二进制证书签名的 ELF/`.so`" |
| `ALLOW_EXTERNAL_NATIVE_CODE` | 同上（该权限服务"加载外部 native 程序/二进制"） |
| `kernel.LOAD_INDEPENDENT_LIBRARY` | 同上（该权限服务"加载二进制证书签名的共享库"）。⚠️ 例外：若 Phase 2 引入自编译的 `node-pty`/`watcher` 原生模块，需回来复评 |
| `*PLUGIN*` 四个权限 | 本工程插件是 **Node 包**，不是鸿蒙插件包 |
| `CUSTOM_SANDBOX` / `RUN_ANY_CODE` / `SANDBOX_ACCESS_MANAGER` / `GET_DEVICE_INDEPENDENT_BINARY_CERT` | 系统级或不可得 |

### 8.4 提交与 Profile 约束

1. 路径：AGC → 开发与服务 → 项目 → 应用 → 项目设置 → **ACL 权限**；勾选后填 `申请原因`（≤256 字）与 `使用场景`。
2. **配额与节奏**：单次最多 30 个权限；审核结果整批返回；**上一批未审完不能提交新批次**。
3. **获批落点**：权限在**创建发布 Profile 时写入**；若 ACL 在 Profile 创建后变化，**必须重建 Profile**。
4. 可用 **试用调试 Profile**（5 天有效期、每应用最多 5 个）在正式 ACL 下来前先做可行性验证。
5. ⬜ **待实测**：全新安装时 JIT 受限权限会被设备策略拒绝 → 需确认规避手段（dsh 的做法是日常用 `hdc app install -r` 覆盖安装绕过）。
