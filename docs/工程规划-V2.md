## 1. 项目概述

### 1.1 一句话定义

把 opencode 的桌面形态移植到鸿蒙 PC / OpenHarmony 桌面：用 `harmonypc-electron` 提供的 Electron-on-HarmonyOS 运行时承载 **opencode v2 的 Node 服务端**，渲染层以**目标形态 ArkWeb（回退形态 Electron Chromium）**同源加载该服务端内嵌的 v2 Web UI，最终打包为可签名分发的 HAP。

## 2. 参考工程调研结论

### 2.1 opencode v2.0.26 上游：服务端与「以服务方式启动」

证据：`../opencode/packages/web/src/content/docs/server.mdx`、`packages/cli/src/commands/{commands,handlers/serve}.ts`、`packages/cli/src/server-process.ts`、`packages/server/src/{process,options,routes}.ts`（✅ 源码核实）。

**v1 → v2 的结构性变化（本工程必须重新定位的地方）：**

| 维度 | v1.4.3（V1 文档） | **v2.0.26（本版）** |
|---|---|---|
| 包结构 | `packages/opencode` | `packages/{core,server,cli,protocol,schema,app,desktop,util,…}`，全部 `@opencode/*` 且 `version = 2.0.26` |
| 服务端入口 | `Server.listen({port,hostname,…})` | `ServerProcess.run({mode,hostname,port,cors})`（`packages/cli/src/server-process.ts`）→ `ServerProcess.start(options)`（`packages/server/src/process.ts`，Effect HTTP） |
| 命令行 | `opencode serve [--port|--hostname|--cors|--mdns]` | `opencode serve [--hostname|--port|--cors|--service|--stdio]`（**无 `--mdns`、无 `opencode web` 命令**） |
| 鉴权 | 密码可选，未设会打印 "server is unsecured" | **密码必填**：`OPENCODE_PASSWORD`/`OPENCODE_SERVER_PASSWORD`，两者皆无则进程内随机生成（`Missing server password` → 失败） |
| API 前缀 | 根路径（`/session`、`/global/health`） | **`/api/*`（协议侧 139 个端点）**、`/openapi.json`；服务信息 `GET /api/info`（原 `/global/health` + `/api/server` 合并） |
| 事件面 | `/event`、`/global/event` | `/api/event`（SSE，首个事件 `server.connected`）、`/api/rpc/{rpcID}/{method}` 等；另有 `/auth/*` 走 API 前置分支 |
| UI 托管 | `server/ui/index.ts` + 构建期 `opencode-web-ui.gen.ts` | `cli/src/services/web-ui.ts` + **内嵌 brotli 归档**（见 §2.3） |
| Node 产物 | `Bun.build` → `dist/node/node.js`（957 文件） | Vite SSR **单文件** `dist-node/opencode.mjs` + `dist-node/assets/**`（见 §2.2） |
| 原生面 | `node:sqlite`、`@lydell/node-pty`、`@parcel/watcher`、`jsonc-parser` | 增加 `@ff-labs/fff-node`（FFI）、`opencode-pty` 助手 ELF、**运行时下载 rg 15.1.0**；条件变体由 3 个扩到 7 个（见 §3.6） |
| 上游桌面端 | `desktop-electron` 进程内 host | `packages/desktop`（Electron 44）：**spawn CLI 背景服务** `opencode serve --service` + 文件凭据 + 主进程注入 Basic；并设 `OPENCODE_DISABLE_EMBEDDED_WEB_UI=true` 自行打包 UI |
| 数据/配置根 | 若干 env | `@opencode/util/global-roots`：`XDG_DATA_HOME`/`XDG_CACHE_HOME`/`XDG_CONFIG_HOME`/`XDG_STATE_HOME` + `os.tmpdir()` |

**服务端契约（本工程直接消费的部分）：**

- `ServerProcess.start(options: ServerOptions, lifecycle?, transform?, remoteURLs?)`：`password` 缺失即失败；`hostname` 默认 `127.0.0.1`；`port` 未给则由 OS 分配（`port 0` 合法）；返回 `{address, shutdown, …}`，`shutdown` 为 `Latch`。
- `ServerOptions` 可注入项：`app{name,version,channel}`、`database{path}`、`pty`、`events{persist}`、`models{url,file,fetch}`、`config{directory,project,file,content}`、`windows{gitbash}`、`fs{filewatcher,fff}`、`simulation`。
- **环境变量契约**（`server-process.ts`，✅）：`OPENCODE_PASSWORD`/`OPENCODE_SERVER_PASSWORD`、`OPENCODE_CLIENT`（写入 `app.name`）、`OPENCODE_DB`、`OPENCODE_CONFIG_DIR`、`OPENCODE_CONFIG`/`OPENCODE_CONFIG_CONTENT`、`OPENCODE_CONFIG_PROJECT_DISABLE`、`OPENCODE_GIT_BASH_PATH`、`OPENCODE_MODELS_URL`/`OPENCODE_MODELS_PATH`/`OPENCODE_DISABLE_MODELS_FETCH`、`OPENCODE_FILEWATCHER_DISABLE`（=`OPENCODE_DISABLE_FILEWATCHER`）、`OPENCODE_DISABLE_FFF`、`OPENCODE_SIMULATE`、`OPENCODE_PTY_HANDOFF`。
- **只需 env 即可关闭的三项能力**：离线 models 快照（`OPENCODE_DISABLE_MODELS_FETCH=1` + 可选 `OPENCODE_MODELS_PATH`；`models-dev` 本身已内嵌 `snapshot.txt`）、文件监听（`OPENCODE_FILEWATCHER_DISABLE=1`）、`fff` 索引（`OPENCODE_DISABLE_FFF=1`）。
- CORS：`packages/server/src/cors.ts#isAllowedCorsOrigin` 在白名单命中时回写头，**不拒绝**来源；同源加载不需要改动。

### 2.2 opencode v2：Node 产物构建链

证据：`packages/cli/script/build-node.ts`、`packages/cli/vite.node.config.ts`、`packages/cli/script/{node-assets,app-assets,verify-artifact}.ts`、`packages/cli/src/node/target.ts`（✅ 源码核实）。

- 入口脚本：`bun run --cwd packages/cli script/build-node.ts`，支持 `--target=<platform>-<arch>`、`--bundle-only`、`--single`、`--app-archive=<path>`、`--skip-install`。
- 流程：`bun install --os=* --cpu=*` → `collectNodeAssets(target)`（node-pty / parcel-watcher / fff / ffi-rs / photon+tree-sitter wasm / 提示音 / `opencode-pty`）→ 写入 `dist-node/assets/<key>` → 生成或复用 **`app-archive.bin`** → `vite build`（SSR 入口 `src/node/index.ts`）→ `assertTextImportsInlined("dist-node/opencode.mjs")` → `verifyArtifact`。
- **`--bundle-only` 只产出 `dist-node/{opencode.mjs, assets/**}`，跳过 Node SEA 打包**（SEA 需 Node 26.4.0 的 `--build-sea`）。**本工程只需 `--bundle-only`**（设备侧不可能执行自备 ELF，§2.5）。
- `--target=linux-arm64` 在 Windows 构建机上即可用（`targets` 白名单已含 `linux-arm64`），此时 `builder` 不解析、**不做 SEA、不做 host 冒烟**——门禁由我们在流水线里自建（§6.4）。
- Vite 配置要点（`vite.node.config.ts`）：`build.target: "node26"`、`ssr.noExternal: true`、`outDir: dist-node`、`entryFileNames: "opencode.mjs"`、`inlineDynamicImports: true`、`resolve.conditions: ["node"]`、`minify: true`；`define` 写入 `OPENCODE_VERSION/CHANNEL/ARTIFACT("cli-node")/CLI_NAME("opencode2-node")/OPENCODE_LIBC/FFF_LIBC`。
- **产物前导（prelude）** 会在运行时注入一批绝对路径 env：`OPENCODE_NODE_ASSETS_DIR`（非 SEA 时 = `dist-node/assets/` 的绝对路径）、`OPENCODE_NODE_PTY_PATH`、`OPENCODE_PARCEL_WATCHER_PATH`、`OPENCODE_PHOTON_WASM_PATH`、`OPENCODE_TREE_SITTER_{,BASH_,POWERSHELL_}WASM_PATH`、`FFF_BINARY_PATH`、`OPENCODE_FFF_FFI_PATH`、`OPENCODE_PTY_BIN`、`OPENTUI_LIBC`，并 `require()` 一次 `OPENCODE_FFF_FFI_PATH` 存到 `globalThis.__OPENCODE_FFF_FFI`（失败静默）。
- 原生资源不会「按需 dlopen 失败就跳过」：`packages/core/src/pty/pty.node.ts` 在**模块顶层**执行 `createRequire(import.meta.url)(process.env.OPENCODE_NODE_PTY_PATH ?? "@lydell/node-pty")` → **加载失败会直接中断整个 bundle 的 import**（§3.6 的补丁 0003 因此是**必需**项）。

### 2.3 opencode v2：Web UI 托管与内嵌归档

证据：`packages/cli/src/services/web-ui.ts`、`packages/cli/src/app-assets.ts`、`packages/cli/src/app-archive.ts`、`packages/cli/script/app-assets.ts`、`packages/app/src/runtime/platform/web.ts`、`packages/desktop/src/main/lifecycle/configure.ts`（✅ 源码核实）。

- 服务端把 UI 与 API **同源托管**：`web-ui.ts` 的 transform 判定 —— `/api`、`/api/*`、`/auth/*`、`/openapi.json` 交给 API（路由未命中 → 404）；**其余路径全部走内嵌 UI**（未命中资源回落 `index.html`，SPA）。
- UI 资产以 **`app-archive.bin`** 形式内嵌：`AppArchive.encode` = 小端 u32 索引长度 + JSON 索引 `{key: [offset,length]}` + 各资产的 **brotli** 正文；服务端按 `accept-encoding` 透传 brotli 字节（仅 `index.html` 解压，因为其 CSP 需要哈希内联主题脚本）。
- 非 SEA 运行时从 **`OPENCODE_NODE_ASSETS_DIR/app-archive.bin`** 读取（SEA 时从内存）；`OPENCODE_LOCAL`（channel=local）时改读 `packages/app/dist` 源资产。
- UI 构建：`buildAppArchive()` → `bun run build`@`packages/app`，注入 `VITE_OPENCODE_SERVER_MODE=origin`、`OPENCODE_CHANNEL`。`packages/app` 的生产构建把服务端地址解析为 **`location.origin`**（`getCurrentServerUrl()`），`VITE_OPENCODE_SERVER_MODE === "none"` 才返回 `undefined`。
- 结论：**只要服务端提供内嵌 UI，`http://<host>:<port>/` 同时提供 SPA 与 `/api`（同源）** —— 零前端工程、零自定义协议、零 preload 桥、零 CORS。上游桌面端走的是相反路线（关内嵌 UI、自己在渲染进程打包 `@opencode/app`、主进程注入 Basic 凭据）；本工程**保留内嵌 UI**。
- UI 侧的 CSP（`web-ui.ts#csp`）：`default-src 'self'; script-src 'self' 'wasm-unsafe-eval' 'sha256-…'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https: blob:; connect-src * data: blob:; worker-src 'self' blob:`。注意 `connect-src *`，比 V1 基线更宽松，同源加载更没有阻碍；但 `worker-src blob:` 说明 UI 会创建 blob worker（二维码扫描等）。

### 2.4 harmonypc-electron：Electron 在鸿蒙上的运行方案

证据：`../harmonypc-electron/README.md`、`ohos_hap/runtime-manifest.json`、`ohos_hap/{AppScope,electron,web_engine}`、`../harmonypc-electron-versions/`（✅ 结构与配置核实；`lib.unstripped/*.so` 为 LFS 指针，未拉取）。

- **它是什么**：华为 Electron 鸿蒙 PC 移植的 **ArkTS 外壳（shell）基线与样例应用**，不是可自举构建的 Electron 源码。真正的引擎是**预编译闭源** `libelectron.so`（v37 stripped 实测 **181,090,576 B**），通过 NAPI 挂进 HAP；另有 `libadapter.so`（7,683,456 B）、`libffmpeg.so`（2,198,224 B）。`electron/libs`、Chromium 资源、启动器 ELF 都不入库（gitignore/LFS），必须由发行版归档补齐。
- **运行时契约清单** `runtime-manifest.json`（✅）：`shellVersion = rc.7-fellow99.baseline.1`、`binaryVersion = v37.2.3-20260825.1`、`genericBundleName = com.huawei.ohos_electron`、三个 SO 的 md5、`shellMarkers`（`kTitleBarHeightVP`、`setWindowDecorHeight`、`idNormalization`、`WebNodeHandleWindow`）、`barrelFile = web_engine/Index.ets`、`bundleNameRewrite.adapters`（4 个 ArkTS 适配文件，各 1 处命中）、`libcxx`（取自 DevEco SDK）。
- **进程模型（实测链路）**：ArkTS 应用进程内 `import adapter from 'libadapter.so'` → `getNativeContext(contextType)` → `runBrowser(vec_args)` 启动平台主循环；每个 Electron 窗口 = 一个 ArkTS UIAbility（`startAbility`，`instanceKey = xcomponentId`）；渲染/GPU/crashpad 走 **OHOS `childProcessManager.startArkChildProcess`**（`CustomChildProcess extends ChildProcess` → `nativeContext.runArkProcess`），**不是 fork/exec**，默认带 `--no-zygote`；能力通过 `JSBind.bindFunction` 双向绑定（44 组）。
- **启动参数全集**（`CommandLineAdapter.ets`）：`--use-gl=egl --enable-features=UseOzonePlatform --ozone-platform=ohos --enable-logging --ozone-dump-file=/data/storage/el2/base/cache/ --no-zygote --user-data-dir=/data/storage/el2/base/files/ --force-renderer-accessibility=basic --disable-gpu-watchdog --disable-features=EnableDrDc --inspect`（**默认开 `--inspect`**，生产包必须关掉；**无 `--no-sandbox`**）。
- **应用代码投放**：`web_engine/src/main/resources/resfile/resources/app/`（只读打包）。**不支持 asar**（全仓库无 asar 相关代码），node_modules 必须预打包进 HAP 并落到该目录。
- **可执行 electron 的两种部署模式**：`executableBinaryPaths: libs/arm64-v8a/electron` → `/data/storage/el1/bundle/libs/arm64/electron`（HAP-bin 模式）；或 `hnpPackages: electron.hnp` → `/data/app/electron.org/...`（HNP 模式）；路径经 module metadata `electron_exec_path_ohos` 传回并作为 `--electron-exec-path-ohos=`。当前 fork 只保留了 `client_id`，启用哪一模式需按发行版归档的 `module.json5` 对照（⬜ 收集脚本落地时确认）。
- **第三方原生 addon**：仅 `arm64-v8a`（`aarch64-linux-ohos`、musl），必须用框架配套 headers + `libshim.a` 重编（`clang --target=aarch64-linux-ohos -D__MUSL__=1 -DV8_ENABLE_CHECKS -DV8_COMPRESS_POINTERS_IN_SHARED_CAGE=1 -DNODE_EMBEDDER_MODULE_VERSION=<n>`），产物放 `electron/libs/arm64-v8a/`；普通 Node ABI 不可用。

### 3.1 骨架来源与目录组织 ✅ 已确认

- **骨架来源**：以 `dsh-desktop-hos` 为**唯一工程框架镜像源**，复制其工程框架与 electron 相关内容（`AppScope` / `electron` / `web_engine` / `hvigor` / `build-profile.json5` / `hvigorfile.ts` / `oh-package.json5` / `code-linter.json5` / `signing.*.sample` / `scripts` 骨架 / `specs` 与 `docs` 规范），再把业务接线改为 opencode。**只镜框架，不搬业务**（对照表见 §4.3）。
- **镜像边界**：继承「目录结构、四阶段流水线形态、幂等补丁机制、overlay 机制、单文件大产物 + 流式解压、`docs/` 四件套、`specs/NNN` 编号规范」；替换「补丁集、插件与技能、overlay 条目、`src-main/` 业务接线」；剔除「`profiles/`（pnpm 装配）、市场运行时、`dsh-dist` 分发形态」（opencode 无对应物）。

### 3.2 服务端宿主形态：**待探针裁决**（三个候选）⬜

V1 选定「utility 进程 sidecar」，其依据（旧工程日志）与 dsh 的真机结论**互斥**（⚠️ 冲突 C1/C2）。本版**不预先拍板**，改为 Phase 0 一次探针定标。

| 候选 | 说明 | 已知证据 |
|---|---|---|
| **(A) utility 进程** | `utilityProcess.fork(src-main/sidecar.js)`，sidecar 内 `import` `dist-node/opencode.mjs` 并 `serve` | 旧工程：utility 内 `spawnSync('sh')` = exit 0（🔶）；dsh：应用域 fork 出的 node 脚本 SIGSYS（✅）→ **该候选生死未知** |
| **(B) 主进程进程内** | `main.js` 内直接 `import` bundle 并 `serve` | dsh 的 Host 就是这个形态，**已在真机长期运行**（✅）；代价「宿主崩溃 = 应用级崩溃」 |
| **(C) `worker_threads`** | 主进程内起 `new Worker()` 跑 bundle | dsh 已用同机制跑 pnpm CLI：**JIT 可用、无证书、无新权限、`process.exit` 只退 worker**（✅）；代价：worker 内不能 `process.chdir`、共享进程内存 |

**决策规则（Phase 0 探针，§10 P0-1 给出测项与出口判据）：**
1. 若 (A) 的「进程内 JS/JIT + 加载 20MB bundle + 起 HTTP 服务」全绿 → **选 (A)**：隔离性最好，sidecar 崩溃不带走 UI，且与旧工程路径一致。
2. 否则若 (B) 全绿 → **选 (B)**（dsh 已验证形态），并把 bash 工具改造成「常驻单 shell + 哨兵行」（§3.8）。
3. 否则 → **选 (C)**，并以 (B) 的进程管理纪律执行。
4. 无论哪一候选，**服务端只在一个宿主内运行**，生命周期与 `before-quit`/`will-quit` 绑定，且必须 fail-visible。

> 记录纪律：探针结论（含失败证据）写入 `docs/真机验证记录.md` 与 `specs/007-runtime-entry/`，不得只留在会话里。

### 3.3 渲染通道：**目标 R2（ArkWeb）+ 回退 R1（Chromium）** ✅ 已确认

| 候选 | 说明 | 判断 |
|---|---|---|
| **R2 ArkWeb**（目标） | ArkTS `Web` 组件加载 `http://<局域网IP>:<port>/`；Electron 只作 **Node 宿主**（隐藏窗口/无窗口） | ✅ **定为目标形态**：① 直接回应上架 P0「必须用 ArkWeb 渲染网页」（§2.5c N1）；② ArkWeb 在应用进程内，**可能**让 `0.0.0.0` + `Host`/`Origin` 改写那套 loopback 补丁整体退役（⬜ 见 P0-2）；③ dsh 已实测 ArkWeb 能完整承载其 SolidJS Web UI |
| **R1 Chromium**（回退） | Electron `BrowserWindow` + `loadURL("http://<局域网IP>:<port>/")` | 已跑通过的形态（V1/旧工程/dsh 0.1.5 前），**保留为可用性回退与对照基线**；上架需按 N1 整改（外链 ArkWeb 化、移除 `browsable`/`viewData`、准备「应用自带本地界面、非浏览器」复审口径） |

**两个通道共同的 UI 事实**（来自 §2.3）：UI 与服务端**同源**（`location.origin` → `/api/*`），因此两条通道**都不需要** preload 桥、不需要 CORS 配置、不需要打包前端工程。

### 3.8 数据、沙箱与工具执行契约

- **沙箱映射**沿用 V1 并适配 v2 的 XDG 根（§5.3）：`HOME`/`USERPROFILE` → `userData`（`/data/storage/el2/base/files`）；`XDG_DATA_HOME`/`XDG_CACHE_HOME`/`XDG_CONFIG_HOME`/`XDG_STATE_HOME` → userData 下的子目录；`TMPDIR` 设 `<userData>/tmp` **并 monkey-patch `os.tmpdir()`**；`PATH` 前置可用工具目录。
- **bash/shell 工具契约（本版新增，dsh 实测结论）**：子进程**退出事件永不触发**、`cp.exec` 永不回调、每 spawn 泄漏 1 个僵尸 → 工具层改用 **常驻单 shell + 哨兵行**：`sh -c '<cmd>; echo "__RC=$?"'`，从 stdout 解析退出码；**不要依赖 `exec`/`execFile`/`exit` 事件**。
- **安全围栏（本版新增）**：子进程同 uid，能读写用户目录且不经上层审批 → **必须在工具层自建路径围栏**（允许根 = 当前项目目录 + 沙箱临时目录），否则整个权限/审批体系被旁路。
- **项目目录授权**：应用只能自由读写自身沙箱；用户目录需**按实际路径**申请授权（`fileShare.activatePermission` / `requestDirectoryPermission`，传**真实路径**，Picker URI 仅临时授权、**每次启动需重新 activatePermission**，卸载即清空）；`Documents`/`Download` 目前为 `normal`/`user_grant`，`Desktop` 为 `system_basic`（**上架须不申请**）。⬜ 目录选择器形态见 §5.6。

### 3.9 插件机制：**沿用 v2 原生机制 + v1 默认关闭安装** ✅ 已确认

v2 的插件不是 dsh 那种「壳自己约定的 ESM 包」，而是一套**内建机制**（✅ 源码核实）。本工程**不新造插件框架**，只决定 v1 开哪一档。

**机制全貌（上游 v2.0.26）：**

| 环节 | 事实 | 源码位置 |
|---|---|---|
| 声明 | 配置 `plugins` 数组：`"<pkg>"` = 启用/安装；`{ package, options }` = 带选项启用；**`"-<target>"` 前缀 = 移除**；支持 `file://` 目标；相对目标按所属配置文件所在目录解析 | `packages/schema/src/config/plugin.ts`、`core/src/config/plugin/source.ts#parse` |
| 目录自动发现 | 对每个**配置目录**扫描其下 `plugin/` 与 `plugins/` 子目录，采纳其中的 `.ts` / `.js` 文件或目录 | `core/src/plugin/source-directory.ts`（`names = ["plugin","plugins"]`）、`config/plugin/source.ts#scan` |
| 配置目录集合 | 全局配置目录 `<XDG_CONFIG_HOME>/opencode`；各项目根目录；兼容目录 `<home>/.claude`、`<home>/.agents`（受 `global` 开关控制） | `core/src/config/discovery.ts` |
| 加载（本地） | 绝对路径目标走插件 source runtime（`sources.read(entrypoint)`），并对其做 fs 监听 | `core/src/plugin/module.ts#load` |
| 加载（npm 包） | 两趟：**① `install:false`** 只 `Npm.resolve`（先激活本地可用插件，未装者记 `pending`）→ **② `install:true`** 真装后再加载 | `core/src/plugin/supervisor.ts#activate` |
| 安装实现 | **纯进程内**：`import("@npmcli/arborist")` → `reify({ save, saveType:"prod", ignoreScripts:true, binLinks:true, audit:false })`；缓存 `<XDG_CACHE_HOME>/opencode/npm/<key>`；EffectFlock 串行化；generation 目录切换 | `packages/util/src/npm.ts` |
| 注册表配置 | 经 `@npmcli/config` 读取 npm 配置（`.npmrc` / `npm_config_*` / `registry`），可配镜像 | `packages/util/src/npm-config.ts` |
| 模块契约 | 默认导出 `{ id, effect }` 或 `{ id, setup }`；SDK `@opencode/plugin`（effect / promise 两式）由产物前导的模块钩子注入（`opencode:plugin-v2*` + `globalThis[Symbol.for("opencode.plugin.v2.*")]`） | `packages/cli/vite.node.config.ts#nodePrelude` |
| 治理 | `ManagedPolicy` 对 `integration.use` / `plugin:<target>` 判 `deny` → 返回 `blocked`，该插件被静默禁用（策略来自 Console 组织连接，本地不可直接写） | `core/src/plugin/module.ts`、`core/src/managed-policy.ts` |
| 失败可见性 | 加载失败进 inventory（`status: "failed"` + `error` + `ref`），经 `GET /api/plugin` 暴露；`plugin.check` / `plugin.update` 走 `PluginUpdate` | `packages/server/src/handlers/plugin.ts` |
| 热重载 | 依赖 `Watcher`；本工程 `OPENCODE_FILEWATCHER_DISABLE=1` → watcher 为空实现，**变更不热重载**（首启加载不受影响） | `core/src/filesystem/watcher.ts` |
| 其他声明入口 | 远端 well-known 集成清单可贡献配置文档（理论上含 `plugins`）；风险与纳管见 §7.5 | `core/src/config.ts#loadWellknown`、`core/src/wellknown.ts` |

**v1 立场：默认关闭安装，只放行「随包/本地」插件。**

| 档位 | 行为 | v1 采纳 |
|---|---|---|
| **L0 全关** | 不声明 `plugins`、不放 `plugin/`、`plugins/` 目录 → 插件通道完全静默 | ✅ **v1 默认** |
| **L1 仅本地** | 只允许绝对路径 / 目录插件（壳专用插件随包投放），依赖在构建期预置（禁 symlink，copy 物化） | ✅ **v1 允许**（Phase 2 落地壳专用插件） |
| **L2 允许安装** | 打开第二趟 `Npm.add`（联网访问 registry + 写 XDG cache + hmdfs 语义面） | Phase 2 起评估，须先过 §7.5 风险项与 O8 |

**为什么 v1 不默认开 L2**：① 安装是「**联网 + 落盘 + 在服务端进程内执行任意第三方 JS**」三合一动作，而服务端本身具备文件读写与命令执行能力；② 我们**没有现成的一键开关**——已核对全部 `OPENCODE_*` 环境变量，**不存在** `OPENCODE_DISABLE_PLUGIN*`，「关闭」只能靠「不声明 + 不投放目录」，若要硬开关必须打补丁（候选 `0005-plugin-gate`，§6.2）；③ 组织策略（`ManagedPolicy`）只在接入 Console 组织策略时才有内容。

**壳专用插件的落点**：opencode 只认配置目录下的 `plugin/`、`plugins/`。因此本工程 `plugins/`（§4.1）是**源码与打包源**，构建期由 `collect-app.mjs` 物化到 `<userData>/config/opencode/plugin/<name>/`（随 `XDG_CONFIG_HOME` 映射，§5.3）；**直接放进 `resfile` 不会生效**。

## 5. 运行架构

### 5.1 进程模型（两段式：Phase 0 探针 → 定标收敛）

**Phase 0 待裁决的三种宿主（并列候选）：**

```
候选 A（utility 进程）                       候选 B（主进程进程内）              候选 C（worker_threads）
EntryAbility                                 EntryAbility                        EntryAbility
 ├─ 主进程（窗口 / 解压 / 钩子）                 ├─ 主进程                            ├─ 主进程
 │   └─ utilityProcess.fork(sidecar.js)        │   ├─ opencode server（同进程）        │   └─ new Worker(bundle-host.js)
 │        └─ import opencode.mjs → serve       │   ├─ 窗口 / ArkWeb                   │        └─ opencode server
 └─ 渲染：ArkWeb(R2) / BrowserWindow(R1)        └─ 渲染：ArkWeb(R2) / BrowserWindow(R1)  └─ 渲染：ArkWeb(R2) / BrowserWindow(R1)
```

**定标后的收敛形态（以 A 为例，B/C 只替换中间那一层）：**

```
EntryAbility（应用进程）
 │  ├─ 环境装配：HOME / XDG_* / TMPDIR(+os.tmpdir patch) / PATH（§5.3）
 │  ├─ 确保产物就位：opencode-dist.tar.gz → 流式解压到 userData（marker 幂等，§6.3）
 │  ├─ 起宿主：fork/worker/同进程 import dist-node/opencode.mjs
 │  │     └─ argv = ["node","opencode.mjs","serve","--hostname","0.0.0.0","--port","<随机>"]
 │  │     └─ env：OPENCODE_PASSWORD / OPENCODE_DISABLE_MODELS_FETCH / OPENCODE_FILEWATCHER_DISABLE …
 │  │     └─ 服务端内嵌 UI 同源托管（`/` → SPA；`/api/*` → API）
 │  ├─ 健康检查：GET /api/info（带 Basic 凭据）
 │  ├─ 请求头钩子（R1 必需 / R2 视探针）：Host/Origin → 127.0.0.1:<port> + 注入 Authorization
 │  ├─ 渲染通道：R2 ArkWeb Web(http://<局域网IP>:<port>/) / R1 BrowserWindow.loadURL(同 URL)
 │  └─ before-quit / will-quit：关闭宿主（含僵尸清理）
 └─ 渲染进程（ArkWeb Web 组件 或 Electron BrowserWindow × N）
      └─ 同源：加载 SPA、调 `/api/*`、订阅 `/api/event`(SSE)
```

**为什么渲染层「先 loading 再加载真实 URL」**：首次启动要解压产物（数十秒量级），直接加载会长时间白屏（沿用 V1/dsh 做法）。

### 5.2 启动时序（失败可见）

```
启动 → [env] 环境装配 → [artifact] 产物就位（含首次解压）
   ├─ 失败 → loading 页显示具体阶段与原因（fail-visible，不静默降级）
   → [host] 宿主创建成功？（A: fork / B: 同进程 import / C: worker）
   → [health] GET /api/info 就绪（超时上限 30s）
   → [load] 加载 http://<局域网IP>:<port>/ → 首屏完成 → 关闭 loading 页
```

规则：**每个阶段都必须可观测**（统一日志前缀 `[oc-desktop]` + hilog 关键字 + loading 页阶段文本）；不允许「卡住但不说」。诊断落点沿用 dsh 纪律（如 `globalThis.__hostError` / `__extractError` / `__renderError`），并在真机用 `hdc shell hilog -x | grep oc-desktop` 取证。

### 5.3 沙箱与目录映射（v2 适配版）

真机沙箱事实（🔶 沿用 V1/旧工程/dsh）：`homedir()` = `/storage/Users/currentUser` **不可写**；`userData` = `/data/storage/el2/base/files`（hmfs，可写）；缓存目录 `/data/storage/el2/base/cache`；`/tmp` 与 `os.tmpdir()` 不可写、`TMPDIR` 无效；symlink `EACCES`；`chmod` 静默失效；`/data`、`/storage` 根 readdir 受限。

| 变量 | 目标 | 理由 |
|---|---|---|
| `HOME` / `USERPROFILE` | `/data/storage/el2/base/files`（userData） | 让「家目录」可写 |
| `XDG_DATA_HOME` | `<userData>/data` | 落地 `opencode/opencode.db` 等（v2 `#global-roots`：`<XDG_DATA_HOME>/opencode`） |
| `XDG_CACHE_HOME` | `<userData>/cache` | 缓存；`global.bin` 落此（rg 下载目录，本工程会禁用） |
| `XDG_CONFIG_HOME` | `<userData>/config` | 配置（亦可显式 `OPENCODE_CONFIG_DIR`） |
| `XDG_STATE_HOME` | `<userData>/state` | 状态/锁（v2 `Flock` 依赖） |
| `TMPDIR` | `<userData>/tmp`，**并 monkey-patch `os.tmpdir()`** | 真机上环境变量对 Node 无效，必须打补丁 |
| `OPENCODE_DB`（可选） | `<userData>/data/opencode/opencode.db` | v2 支持显式指定 DB 文件 |
| `PATH` | 前置可用工具目录（`/system/bin`、`/data/service/hnp/bin` 等），其余保持系统默认 | bash 工具要能找到 `sh`/`grep` 等 |
| `OPENCODE_CLIENT` | `desktop` | 与上游 desktop 一致（⬜ 对行为的实际影响） |
| `OPENCODE_SERVER_PASSWORD` / `OPENCODE_PASSWORD` | 随机密码（写入 sidecar env） | 见 §5.4 |

补充规则：**优先用绝对路径调用外部命令**（`/system/bin/sh`、`/system/bin/toybox`），不要依赖 PATH 查找（dsh 实测 PATH 中 `/usr/local/bin`、`/usr/bin`、`/data/app/bin` 都不存在）。

### 5.4 网络与安全

| 项 | 方案 | 状态 |
|---|---|---|
| 绑定地址 | 服务端 `--hostname 0.0.0.0` + 随机高位端口 | **必需**（loopback 隔离） |
| UI 访问 | `http://<局域网IP>:<port>/`（选非 internal 的 IPv4，回退 `127.0.0.1`） | **必需** |
| 鉴权 | `OPENCODE_PASSWORD`（v2 **强制**密码，天然满足）；R1 由主进程钩子注入 `Authorization: Basic …`，R2 由 ArkWeb 侧处理 ⬜ | ✅ 必需 |
| 请求头改写 | R1：对发往该 `host:port` 的请求把 `Host`/`Origin` 改为 `127.0.0.1:<port>`（继承 dsh `installLoopbackHeaderRewrite` 思路）；R2：⬜ 由 P0-2 探针判定是否仍需 | ⬜ |
| 非安全上下文 | `http://<局域网IP>` 不满足安全上下文 → `crypto.subtle`/Service Worker/通知可能受限；R1 可用 `app.commandLine.appendSwitch("unsafely-treat-insecure-origin-as-secure","http://<ip>:<port>")` 提升为可信来源；R2 侧 ⬜ 同探针 | ⬜ **本版新增** |
| 代理 | `NO_PROXY`/`no_proxy` 追加 loopback 与局域网地址；`app.commandLine.appendSwitch("proxy-bypass-list","<-loopback>")` | 🔶 沿用 |
| 局域网暴露面 | 绑 `0.0.0.0` = 同网段可见，且该服务具备文件读写与命令执行能力 | **必须**有密码（已满足）+ 随机端口 + 不启用 mDNS；⬜ 评估是否可用 ArkTS 侧白名单/端口收敛 |
| 证书/CA | 系统 CA 行为未验证（旧工程曾观测 `tls.setDefaultCACertificates` = `undefined`） | ⬜ 见 O4 |
| 生产开关 | 运行时默认带 `--inspect`（§2.4）→ **生产构建必须移除**；`remote-debugging-port` 同理 | ✅ 必做 |

### 5.5 渲染通道细节

| 项 | R2（ArkWeb，目标） | R1（Chromium，回退） |
|---|---|---|
| 载体 | ArkTS `Web` 组件（应用进程内） | Electron `BrowserWindow`（独立渲染进程） |
| URL | `http://<局域网IP>:<port>/` | 同左 |
| 必备配置 | `domStorageAccess(true)`、`databaseAccess(true)`、明文 HTTP 策略（⬜ `cleartextTraffic`） | 无（Chromium 默认） |
| 注入 | 必要时 `javaScriptOnDocumentStart` | 必要时 preload/executeJavaScript |
| 合规 | **符合上架「必须用 ArkWeb」口径** | 需按 N1 整改（外链 ArkWeb 化、移除 `browsable`/`viewData`、复审口径） |
| 与 loopback 的关系 | ⬜ 可能免去头改写 | 必须 0.0.0.0 + 头改写 |
| 图标/托盘/菜单 | ArkTS 侧自行承担（沿用 dsh 的 `statusBarView` 等范式） | Electron `Menu`/`Tray`（2in1 语义有限） |

### 5.6 项目目录与授权 ⬜ 待实测定型

opencode 的「项目」语义由**目录**决定（v2 `GET /api/location`、`GET /api/project`）。设计：

1. 应用启动后由 ArkTS 侧弹出**目录选择器**（`filePicker`/`fileShare`），用户选定工作目录；
2. 授权走 `fileShare.activatePermission` / `requestDirectoryPermission`，**必须传实际路径**；Picker URI 仅临时授权，**每次启动需重新授权**；
3. 选定目录传递给宿主，作为服务端的项目根 / 初始目录（v2 支持 `config.directory`）；
4. UI 内切换项目时复用同一授权通道。

## 7. 能力范围与降级

### 7.1 v1 In scope（必须达成）

1. HAP 可安装启动，进入 **OC Desktop** 窗口，无白屏、无闪退。
2. opencode v2 服务端在宿主内就绪，`GET /api/info` 通过。
3. **Web UI 全功能可用**：会话列表/创建、发消息、流式响应、工具调用可视化、权限询问、diff 查看、主题、多语言。
4. **会话持久化**：重启应用后会话仍在（better-sqlite3 → XDG 数据目录）。
5. **项目目录选择与授权**：用户能在应用内选定工作目录并让服务端以该目录为项目根。
6. **bash 与文件类工具可用**：读取/写入/搜索项目文件、执行 shell 命令（宿主内 spawn `/system/bin/sh` + 哨兵行 + 工具层路径围栏）。
7. **构建可复现**：一条命令链从零产出签名 HAP，且 host 侧 Node 22.17 门禁全绿。
8. 分发形态：tar.gz + SHA-256 marker 的运行时解压机制稳定。

### 7.2 v1 Out of scope（Phase 2+）

| 项 | 原因 | 计划 |
|---|---|---|
| 原生终端面板 / PTY | **平台级不可用**（SELinux 拒 `forkpty`/`openpty`/`popen`，`EACCES`），无官方应用级 API | 不作为规划项；如需，只能走「非 PTY 的伪终端交互」另案评估 |
| 内容搜索（`fff` / `rg`） | `fff` 需 Node FFI（`--experimental-ffi`，Node 26 特性）；`rg` 需运行时下载并**执行** ELF（用户目录不可 exec，自有 ELF 需二进制证书） | v1 优雅降级（空结果 + 明示）；Phase 2 做 `#fff` 纯 JS 变体（补丁 0004） |
| `git` 集成 / VCS | 设备无 `git`，且随包 ELF 不可执行 | Phase 2 评估 isomorphic-git 类纯 JS 方案 |
| worktree / 多工作区 | 依赖 VCS 与链接语义（symlink/hardlink 均不可用） | Phase 2+ 评估 |

### 7.3 鸿蒙能力缺口与降级表

| 缺口 | 根因层 | v1 降级 |
|---|---|---|
| 应用域子进程 JIT 被拦（SIGSYS） | L1（seccomp） | 宿主形态探针定标（§3.2）；若子进程不可用则服务端进主进程/worker |
| `node:sqlite` 无 binding | L1（华为定制 Node） | `#sqlite` ohos 变体 → better-sqlite3 |
| PTY 不可用 | L1（SELinux） | 打桩（UI 不提供终端面板） |
| rg 不可执行 | L1（用户目录不可 exec + 二进制证书） | 搜索降级 + 空结果明示；Phase 2 纯 JS 变体 |
| fff 需 FFI（Node 26） | L1 | `OPENCODE_DISABLE_FFF=1` + 搜索降级 |
| 无 `git` / `rg` / `bash` / `curl` | L1 | 依赖 toybox `sh`（178 applet）；工具内部走 Node 实现或优雅降级 |
| `symlink` `EACCES` | L1 | 一律 copy 物化 |
| `hardlink` `EPERM` | L1 | 原子写走 `rename`，禁用 link 分支 |
| `chmod` 静默失效 | L1 | 写入后**回读校验**，不一致即报 `FS_IO_ERROR` |
| `Documents`/`Download` 需用户授权 | L1 | 首次引导授权 + 提示重启应用 |
| loopback 隔离 | L1 | 绑 `0.0.0.0` + 局域网 IP（+ R1 头改写） |
| 子进程退出事件不触发 | L1 | 常驻单 shell + 哨兵行；不依赖 `exec`/`exit` 事件 |
| 数万小文件入 HAP 不可行 | L2 | tar.gz + 流式解压 + SHA-256 marker |
| 无 root / 无 faultlog | L1 | 自建结构化日志 + 阶段化 loading 页 + CDP 探针 |
| 后端常驻语义弱（2in1 最小化不算后台） | L1 | 不做后台常驻；退出即退出 |

### 7.4 两条专项说明

**a) 内容搜索（`/api/find*`）**：v2 的选择逻辑是 `Fff.available()` 为真且（有 VCS 且非家目录）→ `fffLayer`，否则 → `ripgrepLayer`；`ripgrepLayer` 的二进制获取顺序是「系统 `rg` → `<cache>/opencode/bin/rg` → 从 GitHub releases 下载 `ripgrep-15.1.0-aarch64-unknown-linux-gnu.tar.gz` 并用 `tar` 解压 + `chmod 755`」→ 设备上三者全不成立（无 rg、下载物是 glibc aarch64 ELF、且用户目录不可 exec）。

处置：**v1 = 明示降级**（搜索返回空 + UI 侧可见的能力提示，禁止静默失败）；**Phase 2 = 补丁 0004**：`#fff` 的 `ohos` 变体提供纯 JS 走查（遍历 + 过滤 + 打分），在 `#fff` 层替代实现即可让 `search.ts` 的既有分支工作。

**b) 终端 / PTY**：平台级不可用（L1）。除打桩外**不做任何迂回规划**；`@lydell/node-pty`、`opencode-pty` 助手均不随包分发。

### 7.5 插件通道与降级

**真机风险矩阵**（与 §3.9 的机制逐项对齐）：

| 环节 | 设备侧事实 | 判定 |
|---|---|---|
| 本地插件（绝对路径 / 目录） | 只需按路径 `import()` + 文件系统读；无子进程、无原生模块 | ✅ 可用（前提：插件本身不使用设备不具备的能力，如 PTY / 外部进程） |
| 插件目录发现 | 只需读配置目录下的 `plugin/`、`plugins/` | ✅ 可用 |
| 热重载 | `Watcher` 被 `OPENCODE_FILEWATCHER_DISABLE=1` 关成空实现（`enabled:false` → `Stream.empty`） | ⚠️ 首启加载正常，**变更不热重载**（改插件需重启服务端/应用） |
| npm 安装（第二趟 `Npm.add`） | 进程内 Arborist：**不 spawn 包管理器**，不受「应用域子进程 SIGSYS」影响；但需**联网访问 registry**，并在 `<XDG_CACHE_HOME>/opencode/npm/` 落盘、`node_modules` 物化 | ⚠️ 未验证（⬜ O8）：hmdfs 上的 hardlink/symlink/chmod 语义、体积、失败可见性 |
| 安装脚本 | Arborist 以 `ignoreScripts: true` 运行（不执行 `postinstall`） | ✅ 减少一条任意代码执行路径 |
| 插件执行 | 在**服务端进程内**执行任意第三方 JS，与服务端同等权限（文件读写 + 命令执行） | ❗ 与 §3.8「shell 绕过围栏」同源问题 → v1 默认不开放 |
| 遥控入口 | 远端 well-known 集成清单可贡献配置文档（理论上含 `plugins` 声明） | ❗ 需纳管（⬜ 实施时确认来源与是否需要禁用） |

**三档降级与落地动作：**

| 档 | 形态 | 落地动作 |
|---|---|---|
| **L0 关闭**（v1 默认） | 不声明 `plugins`；不投放 `plugin/`、`plugins/` 目录 | 无需补丁。文档与 README 明示「本版不启用插件」；`GET /api/plugin` 返回空清单属**预期行为**，UI 与验收脚本不得当作故障 |
| **L1 仅本地插件**（v1 允许） | 壳专用插件在构建期物化到 `<userData>/config/opencode/plugin/<name>/`；其依赖在构建期预置（禁 symlink，copy 落盘） | `collect-app.mjs` 负责投放与校验；插件必须自证不依赖 PTY / 外部进程 / 原生模块 |
| **L2 允许安装**（Phase 2） | 配置声明 npm 包 → 服务端第二趟自动安装 | 先过 O8；建议同时提供**硬开关**（候选补丁 `0005-plugin-gate`）与 registry 镜像（`.npmrc`）；安装/加载失败须在壳层可见 |

## 8. 权限与签名

### 8.1 必须申请（ACL，受限权限）

判定规则（🔶 沿用 dsh 的权威口径）：**受限权限 ⟺ `provisionEnable == true` 且 `availableLevel ∈ {system_basic, system_core}`**。仅凭名称含 `kernel.` 就主张申请是错的。

| 权限 | level / since | 状态 | 用途 |
|---|---|---|---|
| `ohos.permission.kernel.ALLOW_WRITABLE_CODE_MEMORY` | system_basic / since 14 / 平板 + 2in1 / 受限 | ⬜ **本包名需新申请** | 启用 Electron/V8 **JIT**，引擎必需，**不可删除**；须同时出现在 `web_engine` 的 `requestPermissions` 与 `definePermissions` |

### 8.2 开放权限（免 ACL，写进 `requestPermissions` 即安装时授予）

`INTERNET`、`GET_NETWORK_INFO`、`KEEP_BACKGROUND_RUNNING`（配合 `backgroundModes: ["taskKeeping"]`）、`READ_WRITE_DOCUMENTS_DIRECTORY`、`READ_WRITE_DOWNLOAD_DIRECTORY`、`FILE_ACCESS_PERSIST`。

### 8.3 本项目**不需要**申请

| 项 | 不申请的理由 |
|---|---|
| **二进制证书（AGC `certType: 4`）** | 本工程**不随包分发并执行自有 ELF**（服务端跑在 Electron 自带 Node 内；搜索/终端均降级） |
| `ohos.permission.ALLOW_EXTERNAL_NATIVE_CODE` | 同上（该权限服务「加载外部 native 程序/二进制」，且仅 2in1、须 ACL） |
| `kernel.LOAD_INDEPENDENT_LIBRARY` | 同上；⚠️ 例外：若 Phase 2 引入自编译的 PTY/watcher 类原生模块，需回来复评 |
| `READ_WRITE_DESKTOP_DIRECTORY` | **`system_basic`，上架障碍** → 不申请（dsh 整改结论） |
| `*PLUGIN*` 四个权限 | 本工程插件是 **Node 包**，不是鸿蒙插件包 |
| `CUSTOM_SANDBOX` / `RUN_ANY_CODE` / `ACCESS_USER_FULL_DISK` / `SANDBOX_ACCESS_MANAGER` / `GET_DEVICE_INDEPENDENT_BINARY_CERT` | 系统级或不可得；**不要**用 `CUSTOM_SANDBOX` 替代进程沙箱 |

> 说明：`better_sqlite3.node` 放在 HAP 的 `libs/arm64-v8a/` 属于**随包原生库**（dsh 0.1.5 上架版本即含该文件），与「执行自有 ELF」是两件事，不需要二进制证书。

### 8.4 提交与 Profile 约束

1. 路径：AGC → 开发与服务 → 项目 → 应用 → 项目设置 → **ACL 权限**；勾选后填 `申请原因`（≤256 字）与 `使用场景`。
2. **配额与节奏**：单次最多 30 个权限；审核结果整批返回；**上一批未审完不能提交新批次**。
3. **获批落点**：权限在**创建发布 Profile 时写入**；若 ACL 在 Profile 创建后变化，**必须重建 Profile**。
4. 可用**试用调试 Profile**（5 天有效期、每应用最多 5 个）在正式 ACL 下来前先做可行性验证。
5. ⬜ **待实测**：全新安装时 JIT 受限权限会被设备策略拒绝 → 需确认规避手段（dsh 的做法是日常用 `hdc app install -r` 覆盖安装绕过）。
6. 上架必须使用**发布证书 + 发布 Profile**（比对 Profile 的 `type`），debug 自签不满足。
